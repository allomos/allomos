# Task-A05-01-ssr-board-import

- **Outcome.** The owner's SSR migration board — every card, workstream, state, label, session and next dependency — can be imported into FlipHopper's model, so FlipHopper's first real project is the one the owner uses today.
- **Mapping.** The SSR project's *workstreams* (W00–W15) become FlipHopper *areas*, and its card IDs are kept as they are. The project may rename "area" back to "workstream" for its own screens (R90).
- **Decisive unknowns.**
  - One-time import or continuous sync during the transition (owner — on the board's Waiting list).
  - The SSR board's current structure: since 2026-09-28 each card has a board-fields table (State, Done, Priority, Depends on, Waiting on, Feature) and the board is generated by `check-board.mjs` — read it again at start (worker).
  - Mapping of SSR labels and "Waiting on" values to FlipHopper states, labels and waiting-on types (worker proposes; owner confirms).
- **Files owned.** `crates/importer/**`, its tests and fixtures, this card.
- **External operations.** None. The SSR repository is **read only**: no writes, commits or hooks run there.
- **Done means mechanically.** Importing the SSR `docs/migration-plan-ssr/` folder yields a model that validates in `crates/core`; a reconciliation report lists every card file and board row with no card dropped or duplicated; unknown or unmappable values are reported, not guessed; tests use synthetic fixtures, not the private board text.
