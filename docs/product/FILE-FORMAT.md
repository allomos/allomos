# Taskbag file format — `allomos/8`

A **contract**: the files inside a taskbag. The Allomos app, the `alm` command and AI agents must all read and write exactly this. Code: `crates/core` (rules) and `crates/store` (reading and writing). Decided by [0007](../decisions/0007-git-like-project-sync.md) and [0010](../decisions/0010-project-data-folder.md).

## In plain words

A taskbag is an ordinary folder of small text files. There is one file for the project, one file per area, one file per iteration (if the project plans by iteration), and one folder per task. Each task folder holds a JSON file for its fields and a Markdown file for its description. Every change is also written down as one small **event** file in `events/`: what changed, who did it and when, so a task's history can be shown. Because they are plain text, Git can show exactly what changed, and anyone can read them.

## Where the taskbag is

- **Always `.allomos/taskbag/`** at the root of the folder the user picks: a code repository, a folder with other files, or an empty folder ([0013](../decisions/0013-product-name-fliphopper.md); renamed from `.fliphopper/seabag/` 2026-10-10, [0015](../decisions/0015-product-name-allomos.md)). `.allomos/` leaves room for other Allomos files later.
- A folder that already holds `project.json` directly is opened as a taskbag as it is; Allomos never creates one there.

- **`README-allomos.md`** next to `.allomos/`: when the app creates a taskbag in a folder that **looks empty** (no entries, or only hidden ones such as `.DS_Store` or `.git`), it also writes this short introduction in the interface's language, so the folder does not look empty to a person. It is written only there, never over an existing file, and never named `README.md`. It is not part of the taskbag; the user may edit or delete it (task `A01-05`).

- **`AGENTS.md` and `CLAUDE.md`** next to `.allomos/`: `alm init` asks the AI agent that runs it to add a short Allomos section, merged with what the files already say (task `A01-14`). When the app creates a taskbag, it offers to open the AI agents it finds with the same request (task `A03-03`); only when the person chooses "Write the files for me", or `alm init --write-agent-files` runs, does Allomos add the section itself telling AI agents to work the tasks with `alm`, headed `## Tasks: Allomos` (no marker lines, owner 2026-10-08). Its text is what `alm brief` prints: a short brief naming the terms Allomos relies on and pointing agents to `alm guide` for details (owner, 2026-10-10). A file is taken to have it already when any heading names Allomos. A missing `AGENTS.md` is created with it; an existing one gets it appended once. A missing `CLAUDE.md` is created as `@AGENTS.md` (Claude Code then reads AGENTS.md); an existing one is left alone when it imports `@AGENTS.md` or has such a heading, and otherwise gets it appended. Nothing already in either file is changed (task `A01-13`).

Allomos never creates a Git repository inside a taskbag; the surrounding repository versions it.

## Layout

```text
.allomos/taskbag/
  .gitignore        keeps .lock and temporary files out of Git
  .gitattributes    keeps `\n` line endings on every computer
  .lock             Allomos's writing lock (never committed)
  project.json
  areas/
    A01.json
    A02.json
  iterations/       optional: a taskbag without it has no iterations
    I01.json
    I02.json
  tasks/
    A01-01/
      task.json
      description.md
      card.md       optional: the task's card file (A00-30)
    A01-02/
      task.json
      description.md
  project-notes.md      what every session must know: running, pitfalls, where credentials live
  events/               one file per change: the history (allomos/3)
    .keep
    2026-10-13-140205-123-k7f3q2.json
  keys/                 each computer's public signing key (allomos/8)
    k-b859c413a2e972a5.json
  checkpoints/          signed fingerprints of the whole taskbag (allomos/8)
    2026-11-08-090000-123-x4p2qa.json
```

- File and folder names use the item's ID.
- Names starting with `.` are not items: readers skip them. `alm init` writes empty `areas/.keep` and `tasks/.keep` so the folders survive a Git clone.
- Files are UTF-8 JSON, pretty-printed with a final newline, so that diffs stay readable.

Listed with `alm labels` (with counts), changed with `alm labels add <name> [--meaning]`, `alm labels remove <name>` (refused while a task carries it: `label_in_use`) and `alm rename label`. Before `allomos/7` this was the progress ladder: a list of names, lowest step first, the top step being the human check. |
| `project_folder` | no | The project folder (code, `AGENTS.md`, `CLAUDE.md`), relative to the folder holding `.allomos/` (`"."` for that folder, `"../app"` for a sibling), or absolute when no relative path exists. Written by the app ([OPEN-FOLDER-FLOW](./OPEN-FOLDER-FLOW.md)). Older `alm` builds refuse a taskbag that has it (`field_unknown`): reinstall `alm`. (Builds since `A01-piano403` read past a field they do not know.) `allomos/5` only: `alm upgrade` moves it into `project_folders`. |
| `project_folders` | no (`allomos/6`) | The project folders (decision [0019](../decisions/0019-several-project-folders.md)), the first being the main one: a list of `{"name": "<short name>", "path": "<path read like project_folder>"}`. A name is lowercase letters, digits and `-`, at most 40, unique in the taskbag (`folder_name_invalid`, `folder_name_taken`). Written by `alm upgrade` (from `project_folder`, named after the folder) and by the open-folder flow; binding more folders comes with `alm folder` (A05-taco639). |
| `task_language` | no | The language new and changed tasks are written in: `"ui"` (follow the language the Allomos app shows; the default, also when the field is missing) or a language code such as `"zh-CN"`. Read and set with `alm task-language`. The app saves its interface language in Allomos's per-user settings (`settings.json` in `~/Library/Application Support/io.allomos` on macOS), outside the taskbag (task `A01-21`). |

- `audit` (no; task `A01-frolic587`, decision [0021](../decisions/0021-audit-trail.md#6-settings) § 6): the project's audit settings, so they travel with the taskbag. Every field is optional and a missing one takes its default; the defaults are not written, so a project that never chose has no `audit`. So far: `identity`, where the identity behind a pseudonym comes from: `"pseudonym"` (the default), `"account"` (the cloud project's account) or `"sso"` (the company's sign-in, OpenID Connect or SAML 2.0); a value this Allomos does not know is kept and read as `"pseudonym"`. `reauthenticate` (`true` only with `account` or `sso`): approving and checking ask for a fresh sign-in. Whatever the level, events only ever hold the pseudonym ID. This Allomos has no cloud projects yet, so `account`, `sso` and `reauthenticate` are refused (`identity_needs_cloud`, `reauthenticate_needs_sign_in`) and the app shows them greyed out; lowering the level or turning `reauthenticate` off needs a reason (`audit_reason_missing`). Changed with `alm audit-settings` or the app's Project settings → Audit, each change an event (command `audit-settings`, kind `project`) with the `audit` field's from and to and a `reason` change when one was given. `separation_of_duties` (task `A01-grotto036`, decision 0021 § 1.2; `true` or left out): the same person or agent may not both do and check, or do and approve, a task. Working on a task is an event of `claim`, `start`, `label`, `done`, `handoff` or `release`, by its `actor.session`, its `by` name, its `actor.person` and its `for` (an agent's work counts as the person's it works for); checking is a `human_check` change's `checker`, or a "by human" label added with `label`, by the person who added it; approving is an `approve` event's `approver` (a withdrawn approval no longer counts). While on, `alm` and the app refuse such a change, in either order (`self_check`, `self_approve`, `work_after_signing`), and a human check without a checker (`checker_unknown`); turning it off needs a reason. `retention_years` (task `A01-stem986`, decision 0021 § 1.2 and § 6 item 5; a whole number from 1 to 100, left out for forever): how long the history is meant to be kept; Allomos removes nothing when records pass it, and `alm audit-settings` says how many events are older (`past_retention`: `{cutoff, events, oldest}`, by the date in each event's file name). `legal_hold` (`true` or left out): while on, nothing in the history may be removed or redacted (`legal_hold_on`). A shorter period, and turning the hold on or off, need a reason (`audit_reason_missing`); a period that is not one is refused (`retention_invalid`). Later tasks add the other switches inside `audit`.
- `handoff` (no, `allomos/2`): when a handoff must be written (task `A03-06`). Every field is optional and missing ones take their defaults: `quota_gate` (percentage of the 5-hour quota left; default 3), `context_gate` (percentage of context used; default 90), `write_when` (text; default "after every meaningful step: a task finished, a finding, a commit, a process started or stopped"), and `overrides`: an agent's or account's own `quota_gate` / `context_gate`, by name (`codex`, `claude/work`); a holder `codex/a01-03` gets the override `codex`. Gates are whole numbers from 0 to 100 (`invalid_percent`). Changed with `alm handoff-rules` or the app's Handoff settings.

## Handoffs (`allomos/2`; in the task since A03-polar770)

Added by task `A03-06`. A handoff is what a session leaves so whoever continues, an agent or a person, does not start blind; it is written for any reader, because the writer does not know who takes over (owner, 2026-10-12).

Since task `A03-polar770` (approver, 2026-10-22) a handoff lives in the task itself, with no file of its own and no change of format (still `allomos/5`). `alm handoff <id> --as <session> --text "<handoff>"` (or `--from <file.md>`) in one change:

- replaces the task's **`handoff_note`** (where it stopped, the one next step, who it waits on);
- with `--evidence "<what>"`, adds `- <YYYY-MM-DD>, <session>: <what>` as the last item under the description's **Evidence** heading (`## Evidence` at any level, or a line that is only `**Evidence**`), or adds `## Evidence` at the end when there is none;
- records an event (command `handoff`) with the changed fields plus `{ "field": "handed_off_by", "to": "<session>" }`, which lives only in the history, like `reopen_note`.

Same holder rule as other changes; several tasks: once for each. An older taskbag may still hold **`handoffs/`** (one file per session, with a `writer` / `tasks` / `written` / `updated` header) and **`handoff-template.md`**: `alm` reads neither. While `handoffs/` holds any file other than hidden ones (`.keep`), the taskbag needs updating: `alm next` says so (`old_handoffs`, `handoffs` in `--json`), the app shows a notice with **Update the taskbag…**, and the request (`agent_move_handoffs_request_in`, versioned `MOVE_HANDOFFS_REQUEST_VERSION`) asks the agent to write what is still useful into the tasks the files name, skip tasks that are done or dropped, then remove the files, the template and the folder, after the person's Go ahead.

- **`project-notes.md`**: what every session must know whatever its task: what is running, pitfalls, where credentials live (never their values, and no personal details such as email addresses or account names: placeholders only, task `A03-29`). A standard part of every taskbag (task `A03-20`): `alm init` creates it; agents edit it directly (the other exception to "never edit the taskbag by hand") and keep it true while the project is built, as Allomos's section in AGENTS.md (`alm brief`, v7) says. `alm next` shows its `## Running` and `## Pitfalls` sections (the first `##` heading starting with that word, any case) and the day the file last changed (its modification time on this computer, UTC); a missing file is said plainly, not an error. `alm handoff` reminds to update it. Both add `project_notes` to `--json` (`file`, `path`, `found`, `changed`, `running`, `pitfalls`).
- A task's `handoff_note` is also set on release (`alm release --note`) and with `alm note`.

## Events (`allomos/3`)

Added by task `A01-17` (R7). Every change Allomos makes to a task, an area, an iteration or `project.json` is also written down as one **event**. History is shown from events, and later the burndown and the timeline are computed from them. Owner, 2026-10-13: one file per change; nothing is invented for changes made before a taskbag started recording.

- **`events/<date>-<time>-<ms>-<random>.json`**, for example `events/2026-10-13-140205-123-k7f3q2.json`: the UTC time of the change, to the millisecond, then six random letters or digits. Two people's changes therefore never share a file name, and Git merges their `events/` folders without a conflict (each side only adds files). Files are never changed or removed once written. `events/.keep` keeps the folder in Git before the first change.

  ```json
  {
    "at": "2026-10-13T14:02:05Z",
    "by": "claude/a01-17-history",
    "via": "alm",
    "command": "claim",
    "kind": "task",
    "id": "A01-17",
    "changes": [
      { "field": "state", "from": "ready", "to": "in_progress" },
      { "field": "holder", "to": "claude/a01-17-history" }
    ]
  }
  ```

| Field | Required | Meaning |
|---|---|---|
| `at` | yes | When, in UTC, to the second. |
| `by` | no | Who: the `--as` name of the agent session or person. For a change in the app (and its companion pages), the person's pseudonym ID, the same as `actor.person`: never the name the person gave the app, which stays on this computer (task `A01-frolic587`, decision 0021 § 2); left out when there is no pseudonym. Events the app wrote before carry that name. Left out when nobody said. |
| `via` | yes | Which writer made the change: `alm` or `app`. |
| `command` | yes | What was run: the `alm` command (`claim`, `add task`, `labels`, `init`…; `migrate` in taskbags updated by A01-32's guided migration) or the app's action (`handoff-rules`, `connect project folder`). |
| `kind` | yes | What changed: `task`, `area`, `iteration` or `project`. |
| `id` | no | The item's ID; for the project, the project's ID. |
| `agent` | no | Which AI agent ran `alm` (task `A03-27`, approver 2026-10-18): `claude` or `codex`, judged from the environment `alm` runs in (Claude Code sets `CLAUDECODE=1`; Codex sets `CODEX_THREAD_ID`, or `CODEX_SANDBOX` / `CODEX_SANDBOX_NETWORK_DISABLED` in its sandbox). Left out when unsure (signs of neither, or of both), for the app's changes, and in events recorded before. |
| `tool` | no | The agent's tool, when the environment tells it: `claude_cli` (`CLAUDE_CODE_ENTRYPOINT=cli`) or `claude_app` (`claude-desktop`). |
| `actor` | no | Who ran it, beyond `agent` and `tool` (task `A01-black004`, decision [0021](../decisions/0021-audit-trail.md#11-always-recorded-no-switch) § 1.1): for an agent, `session` (its own session ID: Claude Code's `CLAUDE_CODE_SESSION_ID`, Codex's `CODEX_THREAD_ID`) and `model` (the exact model ID it named with `alm --model`, or the one its session named before on this computer), and, since task `A01-urchin867`, the rest of the AI details: `effort` (`alm --effort`, or Claude Code's `CLAUDE_EFFORT`), `permission_mode` (`alm --permission-mode`, for example `auto`), `rules` (the commit hash of the `AGENTS.md` it works under, `alm --rules`) and `alm` (the writing `alm`'s version, as `alm --version` gives it); for a person (in the app, or with `alm` where no agent was seen), `person`: their pseudonym ID, and nothing else. In an agent's event `model`, `effort`, `permission_mode` and `rules` are always there, written `"unknown"` when the agent did not say, never guessed; the other parts are left out when unknown. Unknown parts are kept. |
| `for` | no | On whose behalf an agent made the change: the pseudonym ID of the person it works for (this computer's person, unless `alm --for` names another). Left out for a person's own change. |
| `approval` | no | The approval ID the change relies on, as the writer named it (`alm --approval`). Structured approvals, which give these IDs, come with task `A01-coach782`. |
| `changes` | yes | One entry per field that changed: `field`, then `from` (left out when the field was empty, or the item new) and `to` (left out when it was emptied). Values are as they are stored, for example `"in_progress"` or a list of labels. A new item lists every field it was created with except its ID; a deleted area or iteration (`delete area`, `delete iteration`, task `A01-29`) lists every field it had, with only `from`. A task's fields come in the task pane's order. |

- **One change, one event, under the same lock.** The writer writes the event, then the changed file; if that write fails, the event is removed. A refused change writes no event, and neither does a change that changes nothing.
- **Where history starts.** `alm init` (and the app's new taskbag) writes the first event, `init`. A taskbag upgraded from `allomos/2` by an earlier Allomos got `events/` and one `upgrade` event; that is when its history starts. A task's History shows "recorded since" the taskbag's oldest event.
- **AI decisions** (task `A03-19`): `alm ai-decided <id> "<text>"` writes an event (command `ai-decided`) with one change, `{ "field": "ai_decision", "to": "<text>" }`, and changes no other file. `alm reviewed <id>` (or the app's **Reviewed** button) writes one event (command `reviewed`) with a change `{ "field": "ai_decision", "from": "<text>" }` for each decision it reviews. A task's decisions **to review** are its `ai_decision` changes with a `to` after its last one without. They are worked out from the events alone, so `task.json` has no field for them, and an older Allomos reads these events like any other (the history shows the field by its stored name).
- **Approvals** (task `A01-coach782`, decision 0021 § 1.1, approver 2026-11-08): `alm approve <id>…` (and Go ahead on `alm confirm --task`) writes, in each task the approval covers, an event (command `approve`, its `approval` field set to the approval's ID) with one change `{ "field": "approval", "to": { "id": "ap-…", "approver": "<pseudonym ID>", "scope": { "tasks": [<IDs>], "plan_sha256": "<hex>", "plan": "description" | "<file name>" }, "at": "<UTC>", "channel": "chat" | "app" | "confirm", "words": "<the person's words>", "expires": "YYYY-MM-DD" } }` (`approver`, `words` and `expires` may be left out). `plan_sha256` is the SHA-256 of the exact plan text approved: with `plan` `description`, one task's description as it is, or several tasks' descriptions each under a `## <id>` line, joined by a blank line; otherwise the text of the file shown, which the taskbag does not keep. `alm withdraw <approval ID>` writes, in each task, an event (command `withdraw`) whose `approval` change has only a `from`: the record withdrawn. Where an approval stands is worked out from the events alone: **withdrawn**; **expired** after its `expires` day (UTC); **plan changed** when a `description` plan no longer has the recorded fingerprint; otherwise it **applies**. The app's **Approve…** in the task pane (task `A01-baker800`) writes the same record, channel `app`, with no `words`; its **Withdraw…** writes the same `withdraw` event with a `reason` change. No file gains a field and the format stays `allomos/7`. The older `approved` events of `alm confirm --task` (A03-37), whose `approval` change is a text, still read and are not listed as approvals; an older Allomos shows the new change by its stored field name.
- **Reopening** (task `A01-50`): `alm reopen <id> --note "<why>"` (or the app's **Reopen…**) turns a `done` or `dropped` task into `ready`, held by nobody, and removes every label except `AI decisions to review` and clears `without_human_check` and `human_check_steps`; its description, handoff note and next dependency stay. Its event (command `reopen`) lists those changes plus `{ "field": "reopen_note", "to": "<why>" }`, which, like `ai_decision`, lives only in the history, so `task.json` gains no field and the format does not change.
- **Branches** (task `A03-22`): a task's **base branch** (the Git branch it starts from and merges back into, by its real name) and **working branch** (the branch the work is done on) are event changes named `base_branch` and `working_branch`: in the `add task` event (the base `alm add task` chose, or the person picked in the app), in the `claim` event (the working branch, and the base of a task that had none), and in a `base` event (`alm base`). A task's branches are the last value each field was given; a change with only a `from` empties it. Like AI decisions they are worked out from the events alone, so `task.json` has no field for them and the format stays `allomos/4`; an older Allomos reads these events like any other. Tasks made before have no base until they are claimed.
- **The agent** (task `A03-27`): `agent` and `tool` are new optional fields; the format stays `allomos/4`, so no taskbag needs moving in. An Allomos built before task `A01-55` reports each event that has them as having an unknown field and leaves it out of the history, until it is updated.
- **Human checks** (task `A01-table778`, decision 0021 § 1.1, approver 2026-11-08): the `checked` event of `alm checked` and the app's **Checked** adds, beside the label change, one change `{ "field": "human_check", "to": { "checker": "<pseudonym ID>" | null, "steps_sha256": "<hex>" | null, "result": "pass" | "partly", "words": "<the person's words>" | null, "where": "local" | "deployed" } }`. `checker` is the pseudonym `alm --checker` names, else the person the agent works for (`for`), else the person who made the change (`actor.person`); `steps_sha256` is the SHA-256 of the task's human-check steps (trimmed) as they were when checked, null when it had none; `where` follows the label given (`deployed` for deployed and verified by human). A failed check is not recorded as `checked` (the task is reopened instead), so `fail` is not written. No file gains a field and the format stays `allomos/7`; older `checked` events have no such change.
- **Who ran it, for whom, under which approval** (task `A01-black004`, decision 0021 § 1.1, approver 2026-11-08): `actor`, `for` and `approval` are new optional fields, so the format stays `allomos/7` (decision 0021's step 1; signing comes with `allomos/8`). Every event `alm` and the app write from this version on carries what they could learn; after a change `alm` lists what it could not (`--json`: `event_missing`, with the codes `model`, `session` and `for`; `reason` since `A01-air289`; `effort`, `permission_mode` and `rules` since `A01-urchin867`), and refuses nothing. **Pseudonyms** (decision 0021 § 2, option A): one per person per project, `p-` and six random letters or digits, made the first time a computer writes to a project and kept in Allomos's settings folder on that computer (`identities.json`, project ID → pseudonym), never in the taskbag; who is behind it is not written anywhere by Allomos. The same folder's `session-models.json` remembers each agent session's model, and since `A01-urchin867` its effort, permission mode and rules (what it last named; Claude Code's `CLAUDE_EFFORT` wins over a remembered effort). **Events recorded before** have none of these fields and are not filled in afterwards: they read and show as before, and the history cannot say who ran them beyond `by`, `agent` and `tool`. An Allomos from `A01-55` on reads past the new fields. **AI details** (task `A01-urchin867`): `actor.effort`, `actor.permission_mode`, `actor.rules` and `actor.alm` are new optional parts of `actor`, so the format does not change; an Allomos built before keeps them as unknown parts.
- **Reasons** (task `A01-air289`, decision 0021 § 1.1, approver 2026-11-08): a change can say why with one more change, `{ "field": "reason", "to": "<why>" }`, which, like `reopen_note`, lives only in the history, so no file gains a field and the format stays `allomos/7`. `alm` adds it to each task event of a command run with `alm --why "<why>"`; `reopen --note`, `recheck --reason`, `wait --on` and `done --without-human-check` give theirs as the reason by themselves. **Asked for** on a task's state change (except the steps forward `claim`, `done` and `checked`), its holder let go, a label taken off, and a change of plan: `iteration`, `blocked_by`, or a `base_branch` it already had; a new item (`add …`) and the taskbag's own upgrades are not asked. Without one, the change is made all the same and `alm` lists it after the change (`--json`: `event_missing`, code `reason`); it refuses nothing. The app's changes do not give one yet. Events recorded before have none and are not filled in afterwards; an older Allomos shows the reason as a change to a field named `reason`.
- **Traceability** (task `A01-fennel617`, decision 0021 § 1.1, approver 2026-11-08): the requirements (their `REQUIREMENTS.md` IDs, `R77`) and decisions (their numbers, `0021`) a task serves are an event change named `traces`, whose `to` is the whole list after the change, requirements first, then decisions, each by number, for example `{ "field": "traces", "from": ["R77"], "to": ["R77", "0021"] }`; a change with only a `from` empties it. `alm trace <id> <ref>… [--remove]` writes it (command `trace`); like the branches it lives in the events alone, so `task.json` gains no field and the format stays `allomos/7`. A task's traces are the last list recorded; `alm show` lists them and `alm traces <ref>` finds the tasks back. `alm` refuses only a reference written in neither form (`trace_invalid`); whether that requirement or decision exists is the agent's to check. An older Allomos shows the change as one to a field named `traces`.
- **Outside effects** (task `A01-job650`, decision 0021 § 1.1, approver 2026-11-08): a deployment, a change to a hosted resource or SQL run on a real target is an event change named `effect` (command `effect`), whose `to` is the whole record: `{ "id": "ef-<six letters or digits>", "target": "<where it acts>", "action": "<what is done>", "rollback": "<how it is undone>", "approval": "<approval ID>" | absent, "result": "<what happened>" | absent }`. It is recorded **before and after**: `alm effect <id> --target … --action … --rollback …` (with the global `--approval <id>`) writes it without a `result` (under way), and `alm effect <id> --of <effect ID> --result …` writes it again, with the record before as `from`; recorded afterwards, everything comes at once. The event's own `approval` is the effect's. A task's effects are the last record of each ID; like the traces they live in the events alone, so `task.json` gains no field and the format stays `allomos/7`. `alm` refuses a new effect without its target, action or rollback (`effect_incomplete`), an effect ID the task does not record (`effect_not_found`) and an approval ID no task records (`approval_not_found`); that no approval is named, or that it no longer applies or covers another task, it tells. `alm show` and `alm effects [<id>]` list them; the app's task pane shows them under **Outside effects**. An older Allomos shows the change as one to a field named `effect`.
- **Exceptions** (task `A01-seed343`, decision 0021 § 1.1, approver 2026-11-08): a control that was skipped is an event change named `exception` (command `exception`, or `done` for one recorded by `alm done --without-human-check`), whose `to` is the whole record: `{ "id": "ex-<six letters or digits>", "kind": "check_not_run" | "without_human_check" | "other", "why": "<why the control was skipped>", "accepted_by": "<pseudonym ID or role>" | absent, "check": "<the check not run>" | absent }`. `alm exception <id> --kind … --why … [--check …] [--accepted-by …]` records one (`--check` is needed for `check_not_run`); `alm exception <id> --of <exception ID> --accepted-by …` completes it later, with the record before as `from`. `alm done --without-human-check "<why>" [--accepted-by <who>]` adds one of kind `without_human_check` to its own event, beside the task's `without_human_check` field. A task's exceptions are the last record of each ID; they live in the events alone, so `task.json` gains no field. `alm` refuses an unknown kind (`exception_kind_unknown`), an exception without why or a check not run without its check (`exception_incomplete`) and an exception ID the task does not record (`exception_not_found`); that nobody is named as accepting the risk, or that `accepted_by` looks like an email address, it tells. `alm show` and `alm exceptions [<id>]` list them; the app's history shows each in one line. An older Allomos shows the change as one to a field named `exception`.
- **Redactions** (task `A01-stem986`, decision 0021 § 6 item 5, approver 2026-11-08): a personal detail written into a task by mistake is removed with `alm redact <id> --field <field>… --reason "<why>" [--approved-by <who>] [--event <file>…]`. Every `from` and `to` of a change of those fields, in the task's events (kind `task`, its `id`; only the `--event` files when given), that differs from the field's current value in the task is replaced by the marker `{ "redacted": "rd-<six letters or digits>" }`, in its own file or in place in a packed month; the current value stays (the person corrects it first). One event (command `redact`) records a change named `redaction`, whose `to` is `{ "id": "rd-…", "fields": [<field>…], "files": [{ "file": "events/<name>.json", "fingerprint": "<the event's fingerprint before>", "fields": [<fields removed from it>] }…], "approved_by": "<pseudonym ID or role>" | absent }`, and the `reason`; never an old value. It is written before the files are changed, so its own `sig.prev` points to the fingerprints before. A redacted event no longer matches its signature, and the next event of its chain points to its fingerprint before: `alm audit` lists it under `redacted` (`{file, redaction, by_event, fields}`) instead of `changed`, and a `prev` or a checkpoint's head equal to a recorded fingerprint before is not a gap. The signature and that fingerprint remain, so someone who guesses the exact old value can confirm the guess; nothing in the files says what it was. Older versions stay in Git history unless it is rewritten. `alm` refuses it while the legal hold is on (`legal_hold_on`), without a field (`redact_field_missing`) or a reason (`redact_reason_missing`), for a field the task's history never changed (`redact_field_unknown`) and an event that is not the task's (`redact_event_unknown`); nobody named as approving it, or `approved_by` that looks like an email address, it tells. Nothing left to remove writes nothing. The app's history shows the marker as "(removed)" and the redaction in one line. An older Allomos shows the change as one to a field named `redaction`, and the markers as values.
- **Change type and risk** (task `A01-palm011`, decision 0021 § 1.1 "Risk class and change type", approver 2026-11-08): `alm classify <id>` (command `classify`) records, each as an event change of its own, `change_type` (`"standard"`: a pre-approved routine change, `"normal"`: approved before it is made, `"emergency"`: made first and approved afterwards), `risk` (`"low"`, `"medium"`, `"high"`), `touches` (a list of `"production"` and `"others_data"`, in that order; an empty list: neither) and, for an emergency only, `approval_due` (`"YYYY-MM-DD"`, the last day, UTC, to record its approval; three days after it was marked, unless `--due` says otherwise; cleared when the task leaves emergency). Each change carries the value before as `from`; the last value recorded wins, and a change with only a `from` clears it. Like the traces they live in the events alone, so `task.json` gains no field and the format does not change. An emergency counts as **approved afterwards** once an approval (`approve` event) that covers the task and is not withdrawn was recorded at or after the event that made it an emergency; until then `alm human` lists it under **To approve afterwards** (`--json`: `to_approve_afterwards`, each `{task, since, due, overdue}`), and `alm show` says so. `alm` refuses only a value not in its list (`classify_invalid`), a date that is not one and `--due` on a task that is not an emergency; whether the classification is right is the agent's and the approver's to judge. An older Allomos shows the changes as ones to fields of those names.
- **Links to code and releases** (task `A01-mint242`, decision 0021 § 1.1, approver 2026-11-08): a commit, branch, merge commit, pull request, CI run or release that goes with a task is an event change named `link` (command `link`), whose `to` is the link: `{ "kind": "commit" | "branch" | "merge" | "pr" | "ci" | "release", "ref": "<hash, name, number or tag>", "url": "<web address>" | absent }`. A link is known by its kind and `ref`; recording it again with another address writes the link before as `from`; a change with only a `from` takes it off. A commit or merge `ref` is its hash in lower case (7 to 64 hexadecimal digits), a PR its number without `#`. `alm link <id> <kind> <ref> [--url <address>] [--remove]` writes it; an agent gives what its version control tool and CI show (`alm` runs no Git, decision 0017). Like the traces they live in the events alone, so `task.json` gains no field and the format stays `allomos/7`. `alm` refuses an unknown kind (`link_kind_unknown`), an empty `ref` or a commit or merge that is not a hash (`link_ref_invalid`), an address not starting with `http://` or `https://` (`link_url_invalid`) and taking off a link the task does not record (`link_not_recorded`); whether the commit or run exists is the agent's to check. `alm show` lists them; `alm links <ref>` finds the task of a commit (a hash of 7 digits or more that either starts with), a reference or an address; the app's task pane shows them under **Code and releases**, each opening at its address. An older Allomos shows the change as one to a field named `link`.
- **Not events:** reading.
- **One-time numbers** (task `A01-58`): a change made with `alm --request-id <id>` adds one more change to each event it writes, named `request_id`, whose `to` is `{"id": "<id>", "input": "<fingerprint of the command's words and who ran it>"}`. When the same number comes again, `alm` finds these events and returns the first result instead of changing anything; the same number with another input is refused (`request_reused`). The number is kept as long as the history; a task's history leaves it out. Like the branches it lives in the events alone, so the format stays `allomos/4` and an older Allomos reads these events like any other.
- **Packed months** (task `A01-59`, approver 2026-10-20): so `events/` does not grow by one file per change forever, `alm` packs the history by itself during any command it runs from the 28th of a month (UTC): every earlier month whose changes are still single files gets one file, `events/<yyyy-mm>.events` (for example `events/2026-09.events`), and those single files are removed. Each line of it is one change, `{"file": "<the single file's name>", "event": {…}}`, in file-name order, so the same changes give the same file on every computer and two computers packing the same month do not conflict. A single file of an already packed month that arrives later is taken in on the next packing. Readers read the packed files and the single files together, each change under its original file name, so the history shows the same as before. The command says what it packed and prints the Git commands that share the packed file and the removed single files. An older Allomos reads only `.json` files in `events/`: it skips the packed months without an error, and until it is updated it shows only the history not packed yet.
- **Pairing a device** (task `A04-02-02`, approver 2026-10-25): when a phone or another computer pairs with the desktop app, or is removed from its paired devices, the app records it in the history of every taskbag a window shows: a `project` event, via `app`, with the command `pair` or `unpair`, a top-level `device` field naming the device, and one change to the field `device` (`to` on pairing, `from` on removal). The format stays `allomos/5`; Allomos versions from `A01-55` on read past `device`. The name is what the person typed on the device, so it travels with the taskbag through Git: the pairing page asks not to use personal details.
- **Unknown fields are read past in events** (task `A01-55`, approver 2026-10-19) and, unlike in the other files, not listed: events are written only by `alm` and the app, never by hand, so a field this Allomos does not know was added by a newer one; reading past it keeps that change in the history. Since `A01-piano403` they are also kept when a month is packed, and a `kind` this Allomos does not know is read (the event belongs to no task, area or iteration it knows) and listed as `value_unknown`. Builds before `A01-55` refuse such an event instead.
- **Checks.** An event file that is not valid JSON, misses a required field or has a value of the wrong kind is reported for that file (`alm history --json` → `issues`) and left out; other events still show.

### Fields and values this Allomos does not know

Task `A01-piano403` (approver, 2026-10-25), so a newer Allomos can add a field or a value without breaking an older one:

- **A field this Allomos does not know**, in `project.json` (also inside `handoff` and its `overrides`), an area, an iteration, a task, or a line of a packed month: the file is read as usual, and the field is listed as a reminder, not an error (`field_unknown`, with the field's name: a newer Allomos may have added it, or its name is mistyped). Events read past their unknown fields without listing them (above).
- **Written back unchanged:** when this Allomos rewrites the file (for example to change a task's state), the unknown fields stay in it as they were.
- **A value this Allomos does not know** for a task's or an iteration's `state`, or an event's `kind`: the item is shown with its value, listed as `value_unknown`, and this Allomos does not change that field; a command that would (`alm claim`, `ready`, `done`, the app's state menu, …) is refused with `state_unknown`. Other changes (a note, the description) keep the value. A value that is not a word in quotes at all is refused (`invalid_choice`).
- **Missing areas, iterations and blocking tasks, and labels not in the label table** are listed as before (a label missing from the table is shown as a table entry and written with the next change of `project.json`) (below); the task still shows.
- **The format number goes up only for a change that would make an older Allomos go wrong** ([§ Format versions](#format-versions)): a file renamed or moved, or an existing field whose meaning changes. A new optional field or a new value does not change it.

## Writing rules (how writers take turns)

Owner's choice A, 2026-10-06 (task `A01-03`).

- **One short lock per change.** Every Allomos writer (`alm` now, the app when it starts editing) takes an exclusive operating-system lock on `.lock` for one change only: read the taskbag, check the rules, write, let go. A second writer waits up to 5 seconds, then gives up with `taskbag_busy`. The operating system drops the lock if the process dies, so a crash never leaves the taskbag locked.
- **Whole files only.** A file is written to a temporary `.tmp-…` file in the same folder, flushed to disk, then renamed over the old one; a new task folder is filled under a temporary name and renamed into place. A reader sees the old file or the new one, never half of one. On macOS a reader that already opened the old file keeps reading the old file whole. On Windows another program (an editor, a virus scanner) that has the file open can make the rename fail for a moment, so it is tried again for up to one second while the writer still holds the lock (task `A07-03`).
- **Readers need no lock.** The app and `alm list` / `show` / `next` read without waiting.
- **`.gitignore`** in the taskbag lists `.lock` and `.tmp-*`. `alm init` and the app both write it; since 2026-10-09 the app, like `alm init`, creates an empty taskbag ([OPEN-FOLDER-FLOW](./OPEN-FOLDER-FLOW.md)).
- **Line endings** (task `A07-03`). Allomos always writes `\n`. It reads `\r\n` the same as `\n`, since Git on Windows may check text files out that way. A new taskbag gets a **`.gitattributes`** (`*.json`, `*.md`, `.gitignore` and `.gitattributes` with `text eol=lf`) so Git keeps `\n` on every computer; `alm init`, the app and the starter project write it. A taskbag made before 2026-10-14 has none; reading still works, and one can be added by hand.
- **Paths in files** (task `A07-03`). A relative path Allomos writes into a shared file (`project_folder` in `project.json`, the taskbag's place in `AGENTS.md`) uses `/`, so the same file works on macOS and Windows; a relative `project_folder` written with `\` is read the same. A path on another Windows drive cannot be relative and is kept as it is.
- The lock only orders Allomos's own writers; a person editing a file by hand is not blocked. The checks below still catch a bad file.

## Checks Allomos makes

Each problem names the **file** and, where it can, the **field**, with a plain explanation. Valid tasks still show when other files have problems.

- **Within one file:** valid JSON; required fields present; valid IDs; the right `format`. Unknown fields and values are listed as reminders and kept ([§ Fields and values this Allomos does not know](#fields-and-values-this-allomos-does-not-know)).
- **Across files:**
  - area IDs and task IDs are unique;
  - iteration IDs are unique;
  - every task's `area` exists, and its `iteration`, when it has one;
  - every task's labels are in the project's label table (or are added to it);
  - every `waiting` task says what it waits on;
  - every `blocked` task names at least one blocking task in `blocked_by` (`blocked_by_missing`), each a task of this taskbag (`blocker_unknown`) and not the task itself (`blocked_by_self`);
  - an iteration's `start` and `end` are real dates written `YYYY-MM-DD`.

## Signed events (`allomos/8`)

Added by task `A01-gusto404` (decision [0021](../decisions/0021-audit-trail.md#3-tamper-evidence) § 3, approver 2026-11-08). Event files are never changed or removed by Allomos, but anyone with the files could; signatures make that show.

- **This computer's key.** Each computer has one Ed25519 signing key (RFC 8032), made the first time it writes to an `allomos/8` taskbag. The private key stays in the operating system's key store and never enters the taskbag: on macOS the login Keychain, item "Allomos signing key" (service `io.allomos.signing`, account `this-computer`), reached through the system's `security` tool; on Windows the Credential Manager, a generic credential `io.allomos.signing/this-computer` kept for this user on this computer (not roaming), holding the private key in hexadecimal (A01-ring220). Where Allomos has no key store yet (Linux), changes are written unsigned and `alm audit` lists them. A test or trial run with `ALLOMOS_SETTINGS_DIR` keeps its key in that folder instead (`signing-key.pk8`), never in the system's key store.
- **`sig`** on every event an `allomos/8` taskbag's writers make, last in the file: `{ "key": "<key ID>", "prev": "<fingerprint>" | null, "value": "<signature>" }`. `value` is the signature (128 hexadecimal digits) over the event **without** `sig`, in canonical JSON (RFC 8785: members sorted, no spaces; `allomos_core::canonical`), so re-indenting or packing a month changes nothing. An event's **fingerprint** is the SHA-256 (hexadecimal) of the whole event, `sig` included, in canonical JSON. `prev` is the fingerprint of the same key's previous event in this taskbag (`null` for its first), so each computer's events form one chain, and removing one from the middle breaks it; two computers never share a chain, so branches still merge without a conflict.
- **`keys/<key ID>.json`**: `{ "key": "k-<16 hex digits of the public key's SHA-256>", "algorithm": "ed25519", "public_key": "<64 hex digits>", "owner": "<pseudonym>", "added": "<UTC>" }`, with optional `device` (a name the person gave; never the computer's own name, which often holds the person's) and `retired` (a retired key stays, so its events can still be checked). The first event a computer signs in a taskbag is followed by its signed `add key` event (kind `project`, one change `key` whose `to` is the key file's content), and the key file is written with it. **Replacing a key** (Settings → This computer → **Replace key…**, A01-ring220) makes a new key, saves it in the key store in place of the old one, and in each recent folder's taskbag that has the old key writes a `retire key` event (kind `project`, one change `key` from the key file as it was to the same with `retired` set; `replaced_by`: the new key's ID), signed by the **old** key as the last of its chain, sets `retired` in the old key file (which stays), and then the new key's `add key` event. The old key's events still check against its file. A taskbag that was not among them gets the new key with this computer's next change there; its old key is not marked retired.
- **`checkpoints/<date>-<time>-<ms>-<random>.json`** (`alm checkpoint`, and one right after `alm upgrade` to `allomos/8`): `{ "at", "git_commit" (when the agent passed `--git-commit`; `alm` runs no version control tool), "sha256", "files", "events", "heads": { "<key ID>": { "file", "fingerprint" } }, "receipts": [], "sig": { "key", "value" } }`, signed like an event. `sha256` is the **taskbag's fingerprint**: SHA-256 over one line per file, `<the file's SHA-256>  <path>` and a newline, sorted by path, of every file in the taskbag except `checkpoints/` and names starting with `.` (the lock, temporary files, `.DS_Store`). `heads` names each key's last event, so a later check finds an event removed from the end of a chain. `receipts` is where an outside witness's time-stamp receipts go (decision 0021 § 3.3); none are made yet.
- **Events before signing.** The `upgrade` event to `allomos/8` is the taskbag's first signed event, and the checkpoint made right after it fixes everything recorded before; earlier events stay unsigned and are listed as "recorded before signing" (decision 0021 § 4, option A). Nothing proves they were not changed before the upgrade.
- **`alm audit`** (decision 0021 § 3.4) reads every event as written (packed months under their single files' names), checks each signature against `keys/` and each key's chain, and each checkpoint's signature and heads, recomputes the taskbag's fingerprint and compares it with the last checkpoint's, and lists what it finds: changes recorded before signing, unsigned changes after it, changes whose signature no longer matches (changed after signing), gaps (a signed change whose `prev` names no change of its key: the one before it is missing, with the key's last change before the gap), forks (two changes following the same one), changes signed by a key not in `keys/`, and checkpoints whose last changes are gone. It also remembers on this computer (settings folder, `seen-checkpoints.json`, by project ID) the last checkpoint it saw, and says when the history no longer holds it ("rewritten since"). Facts only: it never says the history is valid or not ("`alm` tells; the agent checks").
- **What it cannot show** (decision 0021 § 3.5): a change made after the last checkpoint by someone holding that computer's key, or the last changes of a chain after the last checkpoint removed; without an outside witness, someone who controls every copy and every key can still rewrite everything.

## Format versions

Added by task `A01-25`. Allomos reads `format` before anything else in `project.json`, because a newer taskbag may have fields this Allomos does not know. Since task `A01-piano403` (approver, 2026-10-25) the number goes up **only** for a change an older Allomos would get wrong: a file renamed or moved, or an existing field whose meaning changes. New optional fields and new values do not raise it: an older Allomos reads past them and keeps them.

- **Readable, changed only after the upgrade** (A01-dime494, approver 2026-10-25; A01-moth111, decision 0020): `allomos/5` and `allomos/6` are read by an Allomos that writes `allomos/7` (a task's old `label` is read as its new label, as below), but every change is refused with `taskbag_to_upgrade` until a person runs `alm upgrade`, so no taskbag mixes the old and new shapes of labels. Without `--confirm` it only says what it will do; `--confirm` writes `allomos/8` (signing starts, below): it moves `project_folder` into `project_folders` (from `allomos/5`), writes the label table, and turns each task's `label` into `labels`: `drafted` and `implemented` are dropped; `locally verified` and `deployed and verified` become `… by agent`; `human verified` (and the older `owner verified`) becomes `deployed and verified by human` when the task's history in this taskbag shows a change to `deployed and verified` first, else `locally verified by human`; a task with AI decisions not yet reviewed gets `AI decisions to review`; the ladder's other steps stay as the project's own labels.
- **Read and written as it is, unsigned, until upgraded** (A01-gusto404): `allomos/7` is read and changed by an Allomos that writes `allomos/8`, without signing. `alm upgrade --confirm` writes `allomos/8` (labels stay as they are), signs the `upgrade` event and makes a checkpoint; from then on every change is signed. New taskbags are made in `allomos/8`.
- **Newer** than this Allomos (`allomos/9` read by an Allomos that writes `allomos/8`; likewise `allomos/8` read by an older Allomos, so it cannot go on writing unsigned changes unnoticed): nothing is read or written. `alm` stops with `taskbag_newer` (exit code 4) and tells the agent to let the person choose: update Allomos now, or let the agent go on working with the files from its own understanding of the newer format. The app shows the problem ("update Allomos now").
- **Older**, in **any** format below this Allomos's (today `allomos/1` to `/4`; `allomos/4` taskbags are moved in once for the iteration state, approver 2026-10-22, task `A01-root343`): nothing is read or written, and no format is "too old" (owner, 2026-10-15, task `A01-45`). Every `alm` command except `init`, `brief`, `guide`, `confirm` and `move-in` stops with `taskbag_to_move_in` (exit code 1), which says the taskbag must be moved in from the app, or with the request `alm move-in` prints.
- **Moving an older taskbag in** works like moving another task system in (`A05-02`): an AI agent does it, not code steps per version.
  1. The app offers **Move the tasks in…** (in the notice above the task list, and in the setup wizard's step 2). It **renames the old folder aside**, keeping the old format in its name, `.allomos/taskbag/` → `.allomos/taskbag-allomos-3/` (`-2`, `-3` … added when that name is taken), and **creates a new, empty taskbag** in its place with the old project's `id`, `name` and `project_folder`. Nothing inside the old folder is changed. If the new taskbag cannot be created, the old folder is renamed back.
  2. The Connect step then gives the chosen agent the **move-in request** (`agent_move_in_request_in`, versioned `MOVE_IN_REQUEST_VERSION`): the conversion request's steps, told that the tasks to move are the old folder's, with everything it holds: `project.json` (ladder, task language, handoff rules), areas, iterations, tasks with their descriptions and status, `handoffs/` and `project-notes.md`. The old `events/` (the history) are not copied, since `alm` records only its own changes: they stay in Git history, and the report and `project-notes.md` name the last commit that holds the old taskbag. An old top label "owner verified" becomes "human verified"; a done task's `finished_without_owner` becomes `without_human_check`.
  3. The agent reads the old files directly, writes the new taskbag only through `alm`, and asks the person once with `alm confirm`. It **removes the old folder only as part of that confirmed plan**, and only when Git history holds it.
  4. Until a task is moved in, a new taskbag with an older one renamed aside beside it (`<name>-allomos-…`) keeps offering **Move the tasks in…**, which opens the Connect step again. `alm move-in` prints the same request; run on the old taskbag itself, the request has the agent rename it aside and create the new taskbag with `alm init` after the Go ahead.
- A taskbag that A01-32's guided migration was updating (`alm migrate`, `alm migrate --finish`, the "being updated" lock, `taskbag_older`, `taskbag_too_old`, `migration_missing`) is now simply older: it is moved in like the others. Those commands and problems are gone.
- **Known limit:** another computer still running an older Allomos keeps writing to the old folder's name until it is updated; people install the new Allomos first.

Allomos's section in a project's `AGENTS.md` / `CLAUDE.md` carries a version too, in its heading: `## Tasks: Allomos (v14)` (v2: the handoff lines, A03-06; v3: the rule for finishing a task and `alm next` listing every free ready task, A03-15; v4: `alm wait --who`, `alm block` / `unblock` and the seven states, A01-31; the human check, `--without-human-check` with `--steps`, `alm human` and `alm checked`, A03-18; v5 to v14, up to card files beside their tasks, A00-30: listed at `SECTION_VERSION` in `crates/store/src/versions.rs`). A heading without one, or with a lower one, is out of date: `alm` adds the warning `instructions_outdated` to every command, telling the agent to replace the section with `alm brief`'s output, and the app shows **Update the instructions…**. Both checks are made only once an agent is connected: the section is in an instruction file of the project folder (the one recorded in `project_folder`, else the folder holding `.allomos/`).

## Not yet in this version

**Older Allomos versions** (before `A01-piano403`) refuse a task with an `iteration` field (`field_unknown`), because they refuse unknown fields. Update `alm` and the app before planning tasks in iterations.
