## 说明

现在给任务设前置任务（`alm block <id> --by <前置任务>`），会把它的状态改成「被阻塞」（`blocked`）。这样有两个问题：

- **原来的状态丢了。** 一个「储备」的任务设了前置任务，就变成「被阻塞」，看不出它原来是储备。前置任务完成后，它自动变成「就绪」，等于没经批准者同意就排进了要做的任务里（2026-11-15 在临时副本里试 `A01-giant040` 时发现）。
- **被阻塞和等人只能二选一。** 一个任务既要等另一个任务做完，又要等人回答，现在只能记一样。

其实「被阻塞」不是任务自己走到的一步，而是一件算得出来的事：它的前置任务里还有没做完的。所以：

**决定（提议）：**

1. **去掉 `blocked` 状态。** `state` 只保留六个：储备（`backlog`）、就绪（`ready`）、进行中（`in_progress`）、等人（`waiting`）、完成（`done`）、放弃（`dropped`）。`blocked_by`（前置任务的列表）是单独的字段，留着不变，不加新字段。
2. **「被阻塞」由程序算出来：** `blocked_by` 里还有没结束的任务（既不是完成，也不是放弃），这个任务就是被阻塞的。界面把它和状态一起显示，例如「储备 · 被 A01-model301 阻塞」。
3. **设前置任务不改状态；前置任务结束后，任务保持原来的状态。** 储备的还是储备，就绪的还是就绪。去掉「最后一个前置任务完成就自动转就绪」的规则。
4. **被阻塞和等人可以同时成立：** 等人的任务也可以有前置任务，显示成「等人 · 被 … 阻塞」。
5. **`alm next` 不列出还被阻塞的就绪任务**（自动监测也不为它开会话）；前置任务都结束后，它不用任何人动手就出现在 `alm next` 里。
6. **旧任务包迁移：** 已经是 `blocked` 状态的任务回到它被阻塞之前的状态（从历史事件里找），找不到就当作就绪；`blocked_by` 留着。

## 影响

- **格式：** `allomos/9`（见 k）；[FILE-FORMAT](../product/FILE-FORMAT.md) 里「七个状态」改回六个，`blocked_by` 改成「任何没结束的任务都可以有」。
- **现有数据：** 只有 `blocked` 状态的任务会被迁移改动；其余不变。
- **规则文字：** `alm guide`（tasks、workflow、terms、customize、commands）、`alm brief` 写进各项目 AGENTS.md 的那一节（本仓库的 AGENTS.md 也改，版本号加一）里说「被阻塞」的地方，都改成新说法：设前置任务用 `alm block`，任务状态不变，前置任务结束后它保持原状态。
- **`alm next` 和自动监测：** 按算出来的「被阻塞」跳过，不再按状态。
- **应用：** 见 j。
